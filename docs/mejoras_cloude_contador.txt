1. RESUMEN EJECUTIVO
El sistema es un MVP funcional con ambiciones de ERP pero con brechas críticas entre sus módulos. Tiene un modelo de datos razonablemente bien estructurado (multi-tenant, UUIDs, Django/DRF), un módulo de contabilidad (plan de cuentas, asientos, libro mayor) y módulos de ventas, compras, inventario y pagos. Sin embargo, los módulos están desconectados entre sí: confirmar una venta no genera asientos contables ni descuenta stock. No hay integración SIFEN, no hay timbrado real, no hay firma digital, no hay CDC válido. El cálculo del IVA es simplificado (porcentaje genérico) sin contemplar las tasas legales paraguayas (10%, 5%, exentas). Para una empresa real en Paraguay, este sistema no es utilizable en producción sin trabajo significativo adicional.
2. EVALUACIÓN POR PUNTO
2.1 MODELO CONTABLE
El módulo apps/contabilidad/ tiene los elementos correctos: PlanCuentas con estructura jerárquica (sintética/analítica, deudora/acreedora), Asiento con líneas debe/haber, validación de balance (validate_balance), SaldoCuenta para acumulados, y CotizacionDiaria para tipo de cambio.
Problemas críticos:
El módulo contable existe como isla. Al confirmar una venta (ventas/views.py → confirmar), el sistema solo crea la CuentaPorCobrar — no genera ningún asiento contable. Lo mismo ocurre con pagos y compras. Esto significa que el libro diario está vacío a menos que alguien cree asientos manualmente, lo cual destruye la trazabilidad automática que cualquier auditor exigiría.
No hay concepto de devengado vs. percibido implementado en la lógica. La venta se "confirma" y genera CxC, pero no hay registro contable del ingreso devengado (Débito CxC / Crédito Ingresos). El pago se confirma y actualiza saldos en la venta, pero no genera el asiento de caja (Débito Caja / Crédito CxC).
No se puede reconstruir un libro diario ni un mayor general a partir de las transacciones operativas porque la contabilización no es automática.
2.2 FACTURACIÓN
El flujo de facturación tiene la secuencia básica correcta: borrador → confirmada → parcial/pagada, con posibilidad de anulación. La numeración usa unique_together = ('empresa', 'numero'), lo cual previene duplicados por empresa.
Problemas:
El campo impuesto_porcentaje en LineaVenta es un decimal libre (default 10%). En Paraguay, el IVA tiene tasas específicas: 10%, 5% y exenta (Ley 6380/19, Art. 83). El sistema debería forzar una de esas tres opciones, no permitir un 7.5% o cualquier valor arbitrario.
No hay concepto de tipo de comprobante (factura, nota de crédito, nota de débito, autofactura, factura de exportación). El modelo Venta es genérico. Para SIFEN se necesitan los 7 tipos de DE (Documento Electrónico) con sus campos específicos.
Los campos timbrado y cdc existen como placeholders vacíos. No hay lógica de validación de timbrado (formato, vigencia, rango autorizado), ni generación de CDC (44 dígitos con dígito verificador), ni firma digital XML, ni comunicación con el SIFEN de la SET.
El recalcular_totales() de Venta calcula total = subtotal + impuestos - descuento, pero el descuento está a nivel de cabecera mientras que los descuentos por línea están en descuento_porcentaje de cada LineaVenta. Hay incoherencia: el descuento de cabecera no se refleja en las líneas y viceversa. En auditoría esto genera diferencias.
No existe nota de crédito ni nota de débito para corregir facturas emitidas — solo anulación completa.
2.3 CLIENTES Y CUENTAS CORRIENTES
La gestión de clientes es razonable: nombre, RUC, tipo (persona/empresa), direcciones múltiples, contactos, límite de crédito, sector, zona.
La CuentaPorCobrar tiene aging (vencidas, resumen), tracking de pagos parciales, y estados adecuados (pendiente, parcial, pagada, vencida, incobrable).
Problemas:
El limite_credito del cliente existe en el modelo pero no se valida en ningún lado. Al confirmar una venta, no se verifica si el saldo pendiente del cliente excede su límite. Esto es una omisión de control interno grave.
El RUC del cliente no tiene validación de formato (dígito verificador del RUC paraguayo). Puede ingresarse cualquier string.
No hay aging report por tramos (0-30, 31-60, 61-90, 90+) como lo requiere cualquier análisis de CxC serio — solo "vencidas sí/no".
2.4 INVENTARIO
El modelo de inventario tiene Almacen, Stock (con cantidad, reservada, mínimo, ubicación) y MovimientoStock (entrada, salida, ajuste, transferencia).
Problema crítico: Al confirmar una venta, no se descuenta stock ni se genera movimiento de salida. Revisé todo el código de VentaViewSet.confirmar() y no hay ninguna interacción con el módulo de inventario. El inventario es puramente manual. Esto significa que el stock y las ventas están desincronizados permanentemente.
Tampoco hay valuación de inventario (FIFO, promedio ponderado, etc.). El costo del producto es un campo estático, no se actualiza con las compras.
2.5 CONTROL INTERNO
Positivo: El sistema tiene auditoría (Auditoria model con datos anteriores/nuevos en JSON, IP, user agent), permisos por rol (admin/vendedor/contador), aislamiento multi-tenant, y transacciones atómicas en operaciones críticas (confirmar venta, confirmar pago).
Problemas serios:
Las facturas en estado borrador pueden ser editadas libremente vía API (PUT/PATCH en VentaViewSet que hereda de ModelViewSet). Una vez confirmada, se puede agregar líneas a ventas que no estén anuladas o pagadas, pero el modelo permite modificar campos de la venta confirmada directamente.
La anulación de ventas pone las CxC en estado "pagada" con saldo 0, lo cual es semánticamente incorrecto — debería ser un estado "anulada" que no se confunda con una CxC efectivamente cobrada. Esto contaminaría reportes de cobranza.
No hay segregación de funciones en el flujo de pagos: el mismo usuario puede crear y confirmar un pago. No hay aprobación de segundo nivel para pagos grandes.
ModelViewSet permite DELETE en ventas por defecto — se podrían eliminar facturas del sistema sin dejar rastro (aunque la auditoría middleware podría capturarlo, depende de su implementación).
2.6 ESTRUCTURA TÉCNICA
Positivo: Django + DRF es una elección sólida. Multi-tenant por FK con TenantManager y TenantQuerySetMixin. UUIDs como PK evitan enumeración. Celery para importaciones async. Docker para deployment. Tests existentes. Swagger/OpenAPI.
Problemas:
LineaVenta no hereda de TenantModel — no tiene campo empresa. Esto rompe el patrón de aislamiento. Si alguien accede directamente a LineaVenta, no hay filtro por tenant.
La lógica de negocio está en las vistas (views.py), no en servicios o managers dedicados. El confirmar de ventas, la actualización de saldos en pagos, todo está en los ViewSets. Esto dificulta reutilización y testing unitario.
CompraDetalle.save() tiene validación comentada/relajada — el comentario dice "Permitir que sea item de compra general" pero esencialmente deja pasar todo.
SQLite como DB de test (test_facturacion.db en el repo) indica que los tests no corren contra PostgreSQL, lo cual puede ocultar problemas de tipos de datos y transacciones.
2.7 CUMPLIMIENTO FISCAL (PARAGUAY)
Para producción en Paraguay faltaría:
SIFEN (Sistema Integrado de Facturación Electrónica): No hay generación de XML según el esquema XSD de la SET. No hay firma digital (certificado digital del contribuyente). No hay comunicación con el web service de la SET (envío, consulta de estado, eventos). No hay generación de KUDE (representación gráfica). No hay manejo de contingencia.
Timbrado: No hay validación de rango de numeración autorizada. No hay control de vigencia del timbrado. No hay relación timbrado ↔ punto de expedición ↔ tipo de documento.
Tasas de IVA: El sistema usa porcentaje libre. Debe restringirse a 10%, 5%, o exenta, con la correcta liquidación (IVA débito fiscal en ventas, IVA crédito fiscal en compras).
Libros obligatorios: No se generan Libro de Ventas, Libro de Compras, ni Libro IVA como lo exige la SET.
Retenciones: No hay soporte para retenciones de IVA ni de renta (IRE/IRP).
Hechauka/Marangatú: No hay exportación en los formatos requeridos por la SET para declaraciones juradas.
3. PRINCIPALES RIESGOS DETECTADOS
RIESGO 1 — Desconexión contabilidad-operaciones (CRÍTICO): Las ventas, compras y pagos no generan asientos. Imposible auditar. Imposible presentar estados financieros derivados del sistema.
RIESGO 2 — Sin control de stock en ventas (CRÍTICO): Se pueden vender cantidades ilimitadas sin verificar existencia. El inventario es ficción.
RIESGO 3 — IVA no normativo (CRÍTICO): Porcentaje libre en lugar de las tasas legales. Cualquier declaración fiscal basada en este sistema tendría inconsistencias.
RIESGO 4 — Sin límite de crédito efectivo (ALTO): El campo existe pero no se valida. Exposición crediticia sin control.
RIESGO 5 — Facturas modificables post-confirmación (ALTO): ModelViewSet permite PUT/PATCH sin restricción por estado en varios campos.
RIESGO 6 — Anulación destruye trazabilidad CxC (MEDIO): CxC anuladas quedan como "pagadas", contaminando métricas de cobranza.
RIESGO 7 — Sin notas de crédito/débito (ALTO): La única corrección posible es anular toda la factura. No hay ajustes parciales, devoluciones parciales, ni bonificaciones.
4. NIVEL DEL SISTEMA
⚠️ MVP (usable con riesgos significativos)
El sistema tiene una arquitectura correcta y módulos bien delineados, pero la desconexión entre ellos lo hace inutilizable para contabilidad real. Funciona como sistema de registro de ventas y cobranzas básico, pero no como sistema de facturación fiscal ni como ERP. La presencia del módulo de contabilidad es prometedora pero está sin integrar.
5. RECOMENDACIONES PRIORIZADAS
CRÍTICO (sin esto, no se puede usar):
Implementar generación automática de asientos contables al confirmar ventas, pagos y compras. El asiento debe crearse dentro de la misma transacción atómica.
Conectar ventas con inventario: al confirmar venta, descontar stock y crear MovimientoStock tipo "salida". Validar disponibilidad antes de confirmar.
Restringir impuesto_porcentaje a las tasas legales paraguayas (10, 5, 0). Agregar campo condicion_iva (gravada 10%, gravada 5%, exenta) en lugar de porcentaje libre.
Bloquear edición de ventas confirmadas vía API (override update/partial_update en ViewSet para rechazar si estado ≠ borrador).
IMPORTANTE (necesario para producción):
Implementar notas de crédito y débito como documentos separados vinculados a la factura original.
Validar límite de crédito del cliente al confirmar ventas.
Agregar validación de RUC paraguayo (dígito verificador).
Implementar aging report por tramos (0-30, 31-60, 61-90, 90+ días).
Extraer lógica de negocio de los ViewSets a una capa de servicios.
Agregar empresa FK a LineaVenta y LineaCotizacion para consistencia del tenant model.
MEJORA FUTURA (para cumplimiento fiscal completo):
Integración SIFEN: generación XML, firma digital, web service SET, KUDE.
Gestión de timbrado con rangos y vigencia.
Generación de Libro Ventas, Libro Compras, Libro IVA.
Exportación Hechauka/Marangatú.
Soporte de retenciones IVA/IRE.
6. CONCLUSIÓN FINAL
¿Usaría este sistema en una empresa real en Paraguay? No en su estado actual. Tiene buena base arquitectónica (Django, multi-tenant, API REST, auditoría), pero los tres pilares de un sistema de facturación — contabilización automática, control de inventario vinculado, y cumplimiento fiscal — están ausentes o desconectados. Es un prototipo avanzado con estructura de MVP. Con las correcciones críticas (puntos 1-4), podría funcionar como sistema interno de registro comercial. Para facturación fiscal real, la integración SIFEN es obligatoria y representa un proyecto en sí mismo.
